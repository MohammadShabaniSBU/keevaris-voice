# V02-02 — Turn identity and idempotency

**Depends on:** V01 (merged)
**Blocks:** nothing in this sprint
**Touches:** `keevaris-voice`

## Problem

`handleFunctionCalls` sends `turn_id: entry.call.id` — Deepgram's own
`FunctionCallRequest` id, used directly as the idempotency key
`VoiceBridgeTurn::storedTurn()` looks up on the API side. That id is
generated by a vendor we've explicitly built `AgentProvider` to make
replaceable. Two concrete problems:

1. **Uniqueness is assumed, not owned.** Nothing in this codebase specifies
   or verifies that Deepgram's function-call ids are unique across a whole
   session, only that they're presumably unique enough for Deepgram's own
   purposes. If two calls in the same session ever collided — retried
   internally by Deepgram, or simply reused across a reconnect — the second
   would silently replay the first's stored answer via `bodyFromTurn()`
   instead of asking a fresh question.
2. **A provider swap breaks the idempotency key's shape.** If `AgentProvider`
   is ever implemented against a different vendor (the entire reason that
   interface exists), whatever id-generation scheme that vendor uses becomes
   this service's idempotency key by accident, with no seam to control it.

## What to build

### Mint the turn id in this service

Add a per-session monotonic counter to `VoiceSession`, incremented once per
`handleFunctionCalls` invocation (not per individual call within a batch —
V01-04's batching already treats one `FunctionCallRequest` as one delegation
round):

```ts
private turnSequence = 0

private mintTurnId(): string {
  this.turnSequence += 1
  return `${this.deps.transport.sessionId}:${this.turnSequence}`
}
```

Call once per `handleFunctionCalls` invocation, use the same minted id for
every call in that batch's delegation requests. `transport.sessionId` is
already the stable per-call identifier `CallRegistry`/`WebTokenService`
established in V01-01 — reusing it here means the turn id is traceable back
to the call it belongs to without a lookup.

### Keep Deepgram's `call.id` where Deepgram needs it

`agent.respondToFunctionCall(call.id, ...)` still uses Deepgram's own id —
that field is Deepgram's protocol requirement for matching a response to its
request, and changing it would break the function-call exchange itself. Only
the value sent as `turn_id` in `DelegationRequest` changes.

### Two calls in one batch, same minted id

If a `FunctionCallRequest` contains two calls (finding 9's scenario), both
delegation requests in that batch carry the *same* minted `turn_id` under
this scheme, which changes `VoiceBridgeTurn::storedTurn()`'s idempotency
behaviour: the second call in the batch would look like a replay of the
first. That's wrong. Append the within-batch index:
`${transport.sessionId}:${this.turnSequence}:${index}`. Verify this against
the two-function-calls fixture from Sprint 1 — it should still produce two
distinct API calls, now with two distinct, deterministic ids instead of
whatever Deepgram happened to assign.

## Acceptance criteria

- [ ] `turn_id` sent to `KeevarisClient.ask()` is minted by `VoiceSession`,
      never read from `call.id`.
- [ ] `agent.respondToFunctionCall`'s first argument is unchanged — still
      Deepgram's `call.id`.
- [ ] Two calls in one `FunctionCallRequest` produce two distinct `turn_id`
      values, both derived from the same session and turn sequence number.
- [ ] A fixture asserts the exact `turn_id` shape sent to the delegation
      stub across two sequential `handleFunctionCalls` invocations in the
      same session (i.e. the counter actually increments across turns, not
      just within one).
- [ ] `two-function-calls-one-request.json` (or its successor from V02-00)
      still passes with the new id scheme.

## Out of scope

- **Persisting the turn counter across a reconnect.** A call that reconnects
  mid-session is not a scenario this codebase handles yet (V01's socket
  lifecycle work treats a dropped Deepgram socket as ending the call); revisit
  only if that changes.
- **Changing what `unit-hq-api` does with `turn_id`.** `storedTurn()`'s
  lookup-by-`turn_id` behaviour is unchanged; this task only changes what
  value arrives in that field.
